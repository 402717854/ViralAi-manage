## 1. 背景与问题

### 1.1 现状

对账链路已闭环：网关流水 → 用量台账（`crm_contract_usage`）→ 账期账单（`crm_contract_bill`）→ 复核 → 结算。但链路末端的"结算"是**纯状态流转**：

```java
// CrmContractBillServiceImpl.settle()  当前实现
校验 bill_status == 2（已确认）
→ updateBillAudit(bill_id, 3 已结算)
```

系统里没有一分钱的实际流转。收付款全靠线下银行转账 + 人工 Excel 记账。

### 1.2 由此产生的四个问题

1. **账实两张皮**：账单"已结算"不代表钱到账，钱到账也不代表账单已结算。财务无法回答"某客户当前还欠多少"。
2. **预付费客户无法闭环**：先充值后消耗的客户，每月需人工从预付款里核减，扣多扣少都可能发生，且无流水可查。
3. **资金动作无留痕**：谁在什么时间给哪个客户加了多少余额、为什么退款，全部散落在聊天记录和表格里，审计无法追溯。
4. **客户维度缺汇总视角**：账单是"合同 + 渠道 + 账期"三维粒度，同一客户分散在多张账单、多个渠道，缺少一个"这个客户整体资金状况"的入口。

### 1.3 本次要解决的核心命题

> 让"客户在平台上的钱"成为系统里的一等公民：余额可查、变动有据、结算自动扣减、账实每日自校验。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 客户余额实时可查，且恒等于流水汇总 | 日终校验任务 100% 一致，不一致即告警 |
| G2 | 账单结算时自动从客户余额扣减，取消人工核减 | 人工核减工单降为 0 |
| G3 | 每笔资金变动可追溯到人、单据、账单 | 任一流水可反查到充值单/账单/退款单 |
| G4 | 财务可按客户查看资金全景 | 客户资金列表 + 账户详情页可用 |

### 2.2 非目标（本期明确不做）

- 在线支付、聚合收款、银行代收（P2）
- 发票开具、税务处理
- 多币种（仅人民币）
- 客户自助门户（客户自己登录查看余额/充值）
- 授信额度、账期管理（P1 预留字段，不实现逻辑）
- 资金收益、利息计算

## 3. 名词与口径

| 名词 | 定义 |
|---|---|
| 资金账户 | 以 `crm_customer.id` 为唯一主体的余额账户。**一个客户一个账户**，跨合同、跨渠道共用 |
| 账面余额 `balance` | 账户当前总额 |
| 冻结金额 `frozen_amount` | 已发起但未完成的扣减占用（P0 恒为 0，仅留字段） |
| 可用余额 | `balance - frozen_amount`，所有扣减/退款判断均以此为准 |
| 充值单 | 客户打款到平台后由业务人员登记、财务审核入账的单据 |
| 退款单 | 将账户余额退回客户的申请单据 |
| 资金流水 | 账户的每一次金额变动的不可变记录，只增不改 |
| 结算扣减 | 账单结算时从客户账户划出应付金额的动作 |

**口径声明（重要）**：资金账户挂在**客户**上，不挂合同、不挂渠道。同一客户的多份合同、多个渠道产生的账单，共用同一余额池。若未来需要"专款专用"，见 §15 待确认问题 1。

### 4.3 数据权限

- **财务角色**：可见全部客户资金（财务对账目录本身只授予财务）。
- **销售角色**：只能看到 `owner_user = 自己` 的客户，且**只读**。
- 实现方式：新增 `CrmFundDataScope`，沿用 `CrmFinanceDataScope` 的渠道维度思路，但过滤字段为 `crm_customer.owner_user`。**不直接复用** `CrmFinanceDataScope`——后者是渠道口径，套到客户维度会把"客户在 A 渠道有账单"误判为无权查看该客户。

## 5. 业务流程

### 5.1 充值流程（对公转账登记 + 财务审核入账）

```
销售/财务登记充值单          财务审核                   系统入账
─────────────────       ──────────────         ─────────────────────────
填写客户、金额、            核对银行到账               写资金流水（入）
付款方、流水号、凭证   →   通过 / 驳回        →      账户余额 += 金额
状态：待审核                驳回需填原因               累计充值 += 金额
                                                     充值单状态 → 已入账
```

**业务规则**

| 编号 | 规则 |
|---|---|
| R1 | 金额必须 > 0，精度最多 8 位小数 |
| R2 | 付款方名称允许与客户名称不一致（代付/关联公司代付），必须记录 `payer_name`，但不阻断 |
| R3 | 银行流水号在同一客户下唯一，重复登记直接拒绝（防同一笔款登记两次）；流水号可为空 |
| R4 | 驳回必须填写原因 |
| R5 | 已入账充值单**不可编辑、不可删除**，纠错只能走人工调账或退款 |
| R6 | 入账必须"写流水 + 改余额 + 改单据状态"在同一事务内完成 |

### 5.2 结算扣减流程（本次核心）

现有入口：账单列表"结算"按钮 → `POST /crm/bill/settle/{id}`。

改造后流程：

```
点击结算
   │
   ├─ 校验账单状态 = 已确认(2)          否则拒绝
   ├─ 校验无未处理差异                   已有逻辑，保持
   ├─ 读取客户账户加行锁（for update）
   │
   ├─ 分支 A：资金扣减（settle_type=1）
   │    ├─ 可用余额 ≥ 应付金额 → 扣减、写流水、账单置已结算
   │    └─ 可用余额 < 应付金额 → 拒绝结算，返回差额
   │
   ├─ 分支 B：线下收款（settle_type=2）
   │    └─ 不扣余额，登记收款方式/凭证号，账单置已结算
   │
   └─ 分支 C：负数账单（差异冲销产生，金额 < 0）
        └─ 自动退回余额，写"冲销退回"流水（方向=入）
```

**业务规则**

| 编号 | 规则 |
|---|---|
| R7 | 结算必须在**同一事务**内完成：扣余额 + 写流水 + 改账单 + 回写商机；任一步失败全部回滚 |
| R8 | 同一账单只允许扣款一次。以流水唯一键 `uk_biz(biz_type, biz_id)` 兜底，重复请求返回"账单已结算"而非二次扣款 |
| R9 | 金额为 0 的账单允许结算，不写流水 |
| R10 | 负数账单结算 = 退款到余额，不再要求余额充足 |
| R11 | 账单需记录**实扣金额** `settled_amount`，允许与应付 `total_sell_amount` 存在差异（线下部分收款场景），差额留待后续账单或人工处理 |
| R12 | 结算后账单进入终态，不允许再次编辑金额 |

### 5.3 退款流程（P1）

```
财务发起退款 → 主管审批（≥5 万强制） → 线下打款 → 登记打款凭证 → 写流水（出）→ 余额减少
```

| 编号 | 规则 |
|---|---|
| R13 | 退款金额 ≤ 可用余额 |
| R14 | 存在"待复核""已确认"账单时，退款前给出风险提示（不阻断，由财务判断） |
| R15 | 必须登记收款账户名、账号、开户行，作为打款依据 |
| R16 | 退款单状态：待审批 → 已退款 / 已驳回；已退款不可撤销 |

### 5.4 人工调账（P1）

用于纠正历史错账、期初余额导入、活动赠送等场景。

| 编号 | 规则 |
|---|---|
| R17 | 调增/调减均需填写**原因**，并上传凭证（可选） |
| R18 | 调减金额 ≤ 可用余额，不允许把账户调成负数 |
| R19 | 调账需财务主管权限，操作留痕到流水（`biz_type = 人工调增/调减`） |

### 5.5 账实自校验

- 定时任务每日 01:00：`账户.balance` 与 `Σ流水.amount` 逐客户比对。
- 不一致立即告警（写差异表 + 日志 + 可选企业微信通知），**不自动修正**——自动修正会掩盖问题。
- 同时校验 `Σ充值 - Σ扣减 - Σ退款 + Σ调增 - Σ调减 == balance`。

### 6.3 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 账户是否独立成表 | **独立表**，不在 `crm_customer` 加余额列 | 客户列表、客户下拉（`/crm/customer/options`）属于高频查询，带金额列会放大结果集；且资金变动需锁账户行，不应连带锁客户主表，否则客户编辑与结算会互相阻塞 |
| 金额精度 | `decimal(20,8)` | 与账单 `total_sell_amount` 完全对齐。若资金用 2 位、账单用 8 位，会出现"账单 123.45678901，扣 123.46"的 0.0032 永久挂账差额，且每期累积 |
| 流水是否可改 | **只增不改**，错误用反向流水冲正 | 审计要求。任何"改历史流水"的实现都会让对账失去可信度 |
| 余额存不存冗余 | 存 `balance` 冗余列，同时保留 `balance_before/after` | 只靠聚合流水算余额，客户一多就慢；冗余 + 日终校验是标准做法 |
| 并发控制 | `select ... for update` 行锁 + `version` 乐观锁兜底 | 结算频率低（每月每客户几张账单），冲突极少，悲观锁逻辑最简单可靠；乐观锁用于防止漏加锁的写路径 |
| 幂等键 | `uk_biz (biz_type, biz_id)` | 一次账单结算只可能有一条扣款流水，数据库层强约束。重复点击、网络重试、并发请求都不会二次扣款 |
| 负数账单 | 走"冲销退回"流水，方向=入 | 差异调账产生的负账单本质是退款给客户，硬编码"扣款"会导致负负得正、余额反向增加 |

## 10. 校验与边界场景

| # | 场景 | 期望处理 |
|---|---|---|
| 1 | 同一客户两张账单并发结算 | 账户行锁串行化，依次扣减，余额不会超扣 |
| 2 | 用户重复点击结算 | 第二次因账单状态已为已结算被拒；即使状态判断被绕过，`uk_biz` 也会拦截插入 |
| 3 | 余额不足 | 拒绝结算，返回差额；前端置灰并引导线下收款 |
| 4 | 账单金额为 0 | 允许结算，不产生流水 |
| 5 | 负数账单（冲销） | 自动退回余额，写"冲销退回"流水 |
| 6 | 客户无资金账户 | 充值/调账时自动创建；结算时按余额 0 处理（严格模式拒绝） |
| 7 | 账单已结算后再次结算 | 拒绝，提示"账单已结算" |
| 8 | 账单处于差异挂起 | 拒绝结算（现有逻辑保持） |
| 9 | 同一银行流水号重复登记 | 唯一键拦截，提示"该银行流水号已登记过充值单" |
| 10 | 退款金额 > 可用余额 | 拒绝，返回可用余额 |
| 11 | 调减导致负余额 | 拒绝 |
| 12 | 金额计算 | 全程 `BigDecimal`，比较用 `compareTo`，禁止 `equals` 与 `double` |
| 13 | 账单所属客户与账户客户不一致 | 拒绝（防御性校验，正常不会发生） |
| 14 | 已结算账单需撤销 | P1 提供"结算撤销"：红冲流水 + 回退余额 + 状态回已确认，需主管权限，且要求账单无后续关联 |
| 15 | 客户被删除 | 账户与流水保留，列表仍可见（标灰），不允许新增充值 |

1. 执行 `crm_customer_fund.sql`（建表 → 加列 → 菜单授权）
2. 发布后端 → 发布前端
3. 用管理员把「客户资金」授予财务角色（脚本已按「有对账账单权限的角色」自动授权，仍需人工确认销售角色是否只读）
4. 期初余额导入：`POST /crm/fund/init`（或页面调账入口），导入后先点一次「账实校验」，确认返回空数组再开账
