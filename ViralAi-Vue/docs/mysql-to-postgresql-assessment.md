# MySQL → PostgreSQL 迁移技术评估

> 评估对象：ViralAi-Vue（RuoYi 3.9.2 / Spring Boot 4.1.0 / Java 17 / MyBatis + PageHelper + Druid）
> 评估日期：2026-10-30
> 评估方式：全仓静态扫描（26 个 Mapper XML、7 个 Maven 模块、4 个 SQL 脚本、34 张表）

---

## 一、结论摘要

**整体可行性：高。该项目属于"方言污染浅、无存储过程、无跨库、无复杂聚合"的类型，替换成本可控。**

关键判断依据：

1. **无存储过程 / 触发器 / 视图 / 自定义函数** —— 迁移中最难啃的部分完全不存在。
2. **无 `GROUP BY` 查询** —— 规避了 MySQL `ONLY_FULL_GROUP_BY` 宽松模式依赖这一最大隐性兼容炸弹。
3. **无动态表名/列名拼接** —— Mapper 中不存在 `${}` 拼接，SQL 注入与结构耦合风险均为零。
4. **方言依赖集中在 RuoYi 框架原生 Mapper**，业务模块（`lion-crm`）仅有 3 处方言调用。

**核心风险不在"改不改得动"，而在三个行为差异**：部门树的 `find_in_set`、`ORDER BY` 的 NULL 排序方向、以及事务隔离级别默认值。这三项不会导致编译或启动失败，但会导致**静默的权限越权、列表顺序错乱、并发幂等失效**。

**建议工作量：** 2 人 × 5～7 人日（含全量回归），其中 DDL 重写约 1.5 人日，Mapper 改造约 1 人日，验证回归约 2～3 人日。

### 方言点分解

| 方言 | 出现次数 | 目标写法 |
|---|---|---|
| `sysdate()` | 34 | `now()` / `CURRENT_TIMESTAMP` |
| `date_format(x, '%Y%m%d')` | 28 | 日期区间比较 或 `to_char(x, 'YYYYMMDD')` |

## 三、改动范围清单

### 3.1 配置层（4 处，必改）

| 文件 | 改动内容 |
|---|---|
| `ruoyi-admin/pom.xml` | `com.mysql:mysql-connector-j` → `org.postgresql:postgresql` |
| `ruoyi-admin/src/main/resources/application-druid.yml` | `driverClassName` → `org.postgresql.Driver`；`url` → `jdbc:postgresql://...`；**`validationQuery: SELECT 1 FROM DUAL` → `SELECT 1`**（PG 无 `DUAL`，不改会连接池启动即失败） |
| `ruoyi-admin/src/main/resources/application.yml` | `pagehelper.helperDialect: mysql` → `postgresql` |
| `docker-compose.yml` / `docker-compose-prod.yml` / `deploy/mysql/init/00-ruoyi-init.sh` | 镜像、`DB_URL`、初始化脚本（`mysql` 客户端 → `psql`） |

### 3.2 Mapper XML 层（17 个文件 / 76 处）

按改造难度排序：

**① 简单全局替换（44 处，机械操作）**
- `sysdate()` → `now()`：34 处，分布在 17 个文件
- `ifnull(` → `coalesce(`：4 处，均在 `SysMenuMapper.xml`

**② 需逐条改写（31 处，需语义判断）**

`date_format` 系列（28 处）—— 两种改法，取舍明确：

```sql
-- 现状（MySQL）：函数包裹列，索引必然失效
AND date_format(create_time,'%Y%m%d') >= date_format(#{params.beginTime},'%Y%m%d')

-- 改法 A（推荐）：区间比较，可走索引
AND create_time >= #{params.beginTime}::timestamp
AND create_time <  (#{params.endTime}::timestamp + interval '1 day')

-- 改法 B（保语义但性能差）：to_char 同样使索引失效，不建议
```
涉及文件：`SysUserMapper`、`SysRoleMapper`、`SysDictTypeMapper`、`SysConfigMapper`、`SysJobLogMapper`、`GenTableMapper`、`CrmModelProductMapper`。

`find_in_set` 系列（3 处）—— **最高风险改写点**，见风险矩阵 R1：
```sql
-- utils/SysDeptMapper.xml:78,82 与 SysUserMapper.xml:83
-- 现状
where find_in_set(#{deptId}, ancestors)
-- 目标
where #{deptId}::text = ANY(string_to_array(ancestors, ','))
```

`str_to_date(concat(...))`（2 处，`CrmModelProductMapper.xml:45,48`）：
```sql
AND a.create_time >= (#{params.beginTime} || ' 00:00:00')::timestamp
```

**③ 反引号（5 处，`SysMenuMapper.xml`）** —— 直接去掉 `` ` `` 即可。`query` 在 PG 中属非保留字（unreserved keyword），可裸用。若团队规范要求绝对保险，改为 `"query"`，但需在建表时也带双引号，反而引入大小写敏感麻烦，**不建议**。

### 3.3 DDL 层（23 张业务表）

语法映射对照：

| MySQL | PostgreSQL |
|---|---|
| `bigint(20)` / `int(11)` / `int(4)` | `bigint` / `integer` / `smallint`（显示宽度需全部移除） |
| `auto_increment` | `generated by default as identity`（推荐）或 `bigserial` |
| `auto_increment=100`（表级初值） | `alter sequence <t>_<c>_seq restart with 100` |
| `comment '...'`（内联列注释） | 独立 `COMMENT ON COLUMN t.c IS '...'` |
| `engine=innodb` / `default charset=utf8mb4` | 删除（PG 无此概念） |
| `key idx_x (col)` | 独立 `CREATE INDEX idx_x ON t (col)` |
| `unique key uk_x (a,b)` | `CONSTRAINT uk_x UNIQUE (a,b)` 或独立 `CREATE UNIQUE INDEX` |
| `tinyint(1)` | `smallint`（**勿用 `boolean`**，见风险 R6） |
| `datetime` | `timestamp`（需明确精度，见风险 R5） |
| `char(1)` | `char(1)` 可用，但注意尾部空格语义（见风险 R7） |

**249 条初始化 INSERT**：需统一改写 `sysdate()` → `now()`；由于全部为无列名形式，**必须先固定列顺序再迁移**，否则列变更后会静默错位。

> 按惯例，RuoYi 官方与社区均有现成的 PG 版初始化脚本可作基线，建议以其为起点人工比对差异，而非从 MySQL 脚本硬翻——可省约 40% 的 DDL 工时。

### 3.4 代码层（2 处）

| 位置 | 问题 | 改动 |
|---|---|---|
| `GenController.java:136` | `SQLUtils.parseStatements(sql, DbType.mysql)` 硬编码 MySQL 解析器，PG 建表语句无法解析 | 改为 `DbType.postgresql`，或根据数据源动态判定 |
| `GenUtils.java` + `GenConstants` | 类型映射基于 MySQL 的 `bigint`/`datetime`/`varchar` 字面量；PG 的 `information_schema.columns.data_type` 返回 `bigint`/`timestamp without time zone`/`character varying` | 扩充 `COLUMNTYPE_*` 常量，覆盖 PG 类型名，否则代码生成器产出的实体字段类型全为 `String` |

## 四、风险矩阵

### 高风险（会导致业务错误，且不报错）

**R1｜`find_in_set` 改写导致数据权限越权** ⚠️ 最高优先级

`sys_dept.ancestors` 是 `'0,100,101'` 形式的物化路径，部门树过滤依赖它。PG 无 `find_in_set`，改写若出现偏差（如字符串拼接方向错误、类型未转换），**查询会返回错误结果而非报错**——表现为某些角色能看到不该看的部门数据。

- 影响面：`SysDeptMapper`（2 处）、`SysUserMapper`（1 处）→ 波及用户管理、数据权限、部门树
- 缓解：改写后必须逐部门层级构造用例验证（根/中间层/叶子/跨层），并对比迁移前后 `select count(*)` 结果集一致性

**R2｜`ORDER BY` 的 NULL 排序方向反转**

MySQL 视 NULL 为最小值；PostgreSQL 默认 `NULLS LAST`（ASC）/ `NULLS FIRST`（DESC）。项目有 26 处 `order by`，且 `create_time`、`update_time` 等列允许 NULL（DDL 中为 `default null`）。

- 现象：列表页按时间倒序时，NULL 记录从末尾跳到首位
- 缓解：对可空列的排序显式加 `NULLS LAST`；或建表时给时间列设 `NOT NULL DEFAULT now()`

**R3｜事务隔离级别默认值不同**

MySQL InnoDB 默认 `REPEATABLE READ`，PostgreSQL 默认 `READ COMMITTED`。

- 影响：现有代码若依赖 RR 的"同一事务内多次读一致"来保证幂等（如先查重再插入），在 PG 下并发时可能穿透。RuoYi 的 `checkUserNameUnique` 类校验 + 业务表的唯一索引组合是典型场景（`crm_supplier_project` 已建唯一索引，属正例；其余表需核查）
- 缓解：显式设置隔离级别，或将"查重+插入"改为依赖数据库唯一约束 + 捕获冲突

**R4｜`varchar(n)` 长度由"静默截断"变为"直接报错"**

MySQL 非严格模式下超长写入被截断；PG 严格执行。`sys_oper_log.oper_param` / `json_result` 均为 `varchar(2000)`，而操作日志的请求参数极易超长。

- 现象：迁移后部分操作日志写入失败，且因日志记录在切面中，可能连带影响主业务事务
- 缓解：迁移前核查历史数据最大长度；这类大文本列建议直接改为 `text`

### 中风险

**R5｜时间精度差异导致排序不稳定**

`datetime`（秒级）→ `timestamp`（微秒级）后，同一秒内多条记录的排序不再稳定，分页可能出现重复/丢行。建议 `timestamp(0)` 保持原精度，或在排序中追加主键兜底。

**R6｜`tinyint(1)` 的类型选择**

共 5 处（`crm_model_billing.status/deleted`、`sys_menu.menu_check_strictly/dept_check_strictly`）。**不要映射为 `boolean`**：MySQL 的 `tinyint(1)` 实际是数值类型，可存 `0/1/2`；若映射为 PG `boolean`，则 `2`、`-1` 等值在迁移时直接失败。应映射为 `smallint`，Java 侧保持 `Integer`。

**R7｜`char(1)` 尾部空格语义**

PG 的 `char(n)` 会补齐空格且比较时忽略尾部空格，MySQL 存储时即去除。现有查询全部为 `= '0'` 形式，**行为一致**；但若未来出现 `like '0%'` 或 `length(status)` 类写法会异常。当前无此用法，风险可控。

**R8｜自增序列与存量数据不同步**

用 `pg_dump`/`pgloader` 迁移数据时，serial/identity 序列的当前值常落后于实际最大 ID，导致插入主键冲突。**必须在迁移后统一执行 `setval` 校正**。

**R9｜Druid `wall` 防火墙对 PG 的 SQL 校验**

`application-druid.yml` 启用了 `wall` filter（含 `multi-statement-allow`）。Druid wall 需按 dbType 加载对应规则，切换后建议先关闭 wall 灰度一轮，确认无拦截误判再开启。

**R10｜代码生成器不可用**

若 `GenController`/`GenUtils` 未同步改造，迁移后"导入表结构生成代码"功能会直接失效（解析异常或字段类型全为 String）。属功能可用性问题，非数据风险。

### 低风险

**R11｜隐式类型转换** —— PG 比 MySQL 严格，`char(1)` 列与数字字面量比较会报错。现有 Mapper 均为 `status = '0'` 带引号，无此问题；但前端若透传排序字段（`orderByColumn`），需确认白名单机制存在。

**R12｜关键字冲突** —— 已核查全部列名，无 PG 保留字硬冲突。`query`、`method`、`path`、`status` 均为非保留字。

**R13｜大小写** —— 现有业务表全部小写，只要建表时不加双引号即无风险。唯一例外是 `QRTZ_*` 大写表名；由于 Quartz 实际运行在内存模式，这 11 张表可直接不迁移，但迁移脚本中若保留，务必加双引号建表，否则 PG 会自动转小写。

## 五、建议实施路径

**阶段 0：基线固化（0.5 人日）**
- 冻结当前 MySQL 版本，`mysqldump` 全量备份
- 采集 `@@sql_mode`、`@@transaction_isolation`、各表行数与关键查询结果集快照（作为回归对照基线）

**阶段 1：Schema 迁移（1.5 人日）**
- 以社区 PG 版 RuoYi 脚本为起点，改造 3 张 crm 表 + 2 张 gen 表
- 数据用 `pgloader` 迁移（其内置 MySQL→PG 类型转换规则可覆盖 80% 的 DDL 差异）
- 迁移后立即执行序列校正与行数比对

**阶段 2：代码改造（1 人日）**
- 配置层 4 处 → Mapper 76 处（先机械替换 44 处，再逐条改写 32 处）→ 代码层 2 处
- 建议保留 mysql 分支能力：用 `databaseIdProvider` 为 Mapper 提供双方言版本，可在灰度期快速回滚（**这是控制整体风险最有效的手段，若一次性切换则无退路**）

**阶段 3：分层验证（2～3 人日）**
1. 启动冒烟：连接池、分页、登录、字典缓存
2. **权限回归（重点）**：多角色 × 多部门层级的数据可见性比对
3. 业务回归：CRM 全流程 + 代码生成器
4. 性能对比：列表页 P95 响应时间，确认 `date_format` 改造后未出现全表扫描

**阶段 4：灰度与回滚预案**
- 双写不可行（方言差异过大），建议采用"停机窗口 + 数据快照回滚"
- 回滚条件：权限回归出现任何不一致，立即回退

## 六、决策建议

**是否值得迁？** 从工程角度看，该项目的 MySQL 依赖属于"表层依赖"——76 处方言点、零存储过程、零动态 SQL 拼接，改造成本落在置信区间内，不构成阻碍。

**但需明确迁移动机**。若目的是：
- **信创/国产化替代** → 成本可接受，按上述路径执行
- **获得 PG 的高级特性**（JSONB、窗口函数、分区） → 建议同步规划利用，否则仅为等价替换，投入产出比低
- **规避 MySQL 许可风险** → 成本可控，值得做

**最需要前置确认的一点**：生产环境 `varchar` 字段是否存在历史超长数据（尤其 `sys_oper_log`）。这一项若不提前核查，会成为上线当天最可能翻车的点——它不在代码里，只在数据里。
